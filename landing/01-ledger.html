Your evals are written from failures you imagined.

The ones that actually happened are sitting in Jira, in three email chains and in an alert nobody connected to either. Swiss stitches them into one story per incident, works out what each one cost, and drafts the eval case for the ones that cost the most.

The method

01 — Stitch

Reports become threads

A Jira ticket, four emails and a Splunk alert are one incident. Swiss joins them automatically only when it is certain — same ticket number, same email chain, same alert refiring. When it is merely likely, a judge proposes and a human decides. Nothing merges on a guess.

02 — Price

Threads get a cost

Each day an incident stayed live counts for more the worse it was. Every extra person pulled in widens it. A fix that failed and came back multiplies it. Counting tickets tells you how loud a problem was; this tells you what it cost.

03 — Draft

Cost becomes an eval case

A thread already records what the assistant was asked, what it wrongly said, and — from whoever verified the fix — what it should have said. That is an eval case. The model drafts it; every quote it cites is checked against the event it came from.

The regression label is not the model's opinion — it is set by the thread's own history, which shows the problem was resolved and returned. The draft then names what should trigger a re-run: embedding model upgrade, knowledge base re-index, vendor platform release.

What it is not

Some threads are not about the model's answers at all.

A run of latency alerts is a real incident and a real cost, but it is not a test case about what the assistant said. Swiss says so, and drafts a threshold check instead of inventing a prompt. A tool that always finds an eval is a tool you cannot trust.
